PACKAGE 937 - the structural layer for branding, currency and terminology
================================================================================

Six files. THREE ARE NEW and must be created by hand in GitHub.

CREATE THESE THREE
------------------
  lib/locale.js                     money, dates, numbers, terms (server side)
  lib/terms.js                      the UK / US / AU / NZ terminology map
  components/TenantProvider.js      the same four functions, client side
  pages/api/tenant-brand.js         the feed between them            <-- also new

REPLACE THESE TWO
-----------------
  pages/_app.js                     wraps the app in TenantProvider
  pages/login.js                    the first real consumer


THE POINT OF THIS PACKAGE
=========================
Nothing visible changes for Rock. This is the plumbing that every branding and
currency package from here on plugs into, plus ONE page converted to prove it
works end to end.

It is deliberately not a library with no consumers. logoUrl() has been
tenant-aware and unused since tenancy was built, and that is exactly how a good
helper becomes dead code nobody trusts.


THE ARCHITECTURE, AND WHY IT IS ONE FEED
=========================================
Two problems that looked separate are the same problem:

  115 client-side "Rock Roofing" strings
  128 client-side pound signs (159 in total across 43 files, plus 368 uses
      of 'en-GB' or 'GBP')

Both are a value that lives on the tenant record and has to reach a component
that CANNOT read it. companyName() and the new locale helpers both call
currentTenant(), which is AsyncLocalStorage, which is Node-only. Importing
either into a component drags async_hooks into the browser bundle.

So: one feed, /api/tenant-brand, carrying name, logo, locale, currency and the
terms map. Server code calls lib/locale.js. Client code calls useFormat() from
components/TenantProvider.js. THE FOUR FUNCTION NAMES ARE IDENTICAL ON BOTH
SIDES - money(), num(), formatDate(), term() - so a line moved between a page
and an API route does not need rewriting, and cannot quietly leave a pound sign
behind.


/api/tenant-brand IS UNAUTHENTICATED. READ THIS.
=================================================
It has to be: the login page needs the company name and logo, and there is no
session on the login page.

Which means it must return NOTHING that is not already public. The fields are
written out one by one rather than spread from the tenant record, precisely so
that a field added to that record later cannot leak by accident. It returns:

  name, logoUrl, localeKey, localeCode, currency, currencySymbol, terms

It does NOT return modules, hosts, sending addresses, user counts or anything
else. If you add a field to the tenant record, it does not appear here unless
someone adds it deliberately.

(For contrast: /api/admin/tenant-setup's GET returns every tenant's id, name,
hosts and modules behind nothing but an admin role. Already on the outstanding
list. Not repeated here.)


TERMINOLOGY - THE PART THAT NEEDS YOUR ATTENTION
=================================================
lib/terms.js maps about 40 terms across UK / US / AU / NZ. Two categories, and
the distinction is the whole reason the file is structured this way:

  COSMETIC   same thing, said differently. "Rooflight" / "skylight". Switches
             freely.

  STATUTORY  legal weight, defined in legislation, often with deadlines
             attached. THESE DO NOT VARY YET - they render in UK English
             everywhere until someone qualified in that market reviews them.

Marked statutory: retention/retainage, application/payment claim, VAT/GST/sales
tax, practical completion, defects liability period, RAMS/SWMS.

Why they are held: NZ's Construction Contracts Act defines "payment claim" and
"payment schedule" with response deadlines. Australia's Security of Payment
regime varies BY STATE. An Australian SWMS is mandated for high-risk work with
prescribed content - a UK RAMS is not a compliant SWMS, so relabelling it would
be worse than leaving it foreign. A wrong local term looks authoritative in a
way that an obviously British one does not.

Also in the file: UK_ONLY (CIS, reverse-charge VAT, CSCS - no equivalents
anywhere, these are modules to switch OFF rather than words to translate) and
NOT_IN_UK (mechanic's liens, lien waivers, ABN withholding - concepts with
nothing to map back to).

I am reasonably confident on the cosmetic terms and NOT confident on the
statutory ones. Treat the map as a first pass for local review, not an answer.


WHAT CHANGED VISIBLY
====================
pages/login.js only. The logo, the page title and the heading now come from the
feed. On Rock they render "Rock Roofing" exactly as before, because that is
what Rock's tenant record says.

Note the logo: logoUrl is empty on Rock's record, so the img is omitted rather
than rendering a broken image. THE LOGO WILL DISAPPEAR FROM THE LOGIN PAGE
until a logoUrl is set on the tenant record. That is deliberate - the
alternative is hard-coding /rock-logo.jpg again - but you should expect it
rather than be surprised by it. To restore it, add to tenant:rock:

  "logoUrl": "https://<a public url for the logo>"

A blob-store URL is the right home for it, and that also fixes the
cron-generated PDFs that currently fetch the logo from the deployment URL.
