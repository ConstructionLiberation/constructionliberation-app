PACKAGE 985 - the CRM activities that were not really there
================================================================================

One file. Complete replacement. INCLUDES 974.

  lib/demoSeed.js

Like 974, this changes what a SEED writes. The demo data already in the
database was written by the old version, so it needs the wipe and re-seed at
the bottom.


WHAT YOU FOUND
================================================================================
Every traffic light grey, and an activity with no due date and nobody
assigned. Not missing data - a field-name mismatch.

  the seeder wrote     dueDate     subject     assignedTo
  pages/crm.js reads   due (x13)   text (x12)  assignee (x12)

So all 190 deals had an activity object the CRM could not read a single
useful field from. The dot defaults to "due in future" when there is no
date, which is why they were all grey rather than all red.

Ran crm.js's own traffic-light rule against both shapes: the new one gives
overdue / today / future correctly, the old one returns "future" for an
activity dated twelve days ago.

The shape is now copied from addActivity() in pages/crm.js - what the app
itself writes when a user adds an activity - rather than invented from the
concept:

  { id, text, due, done: false, assignee, author }

Inventing plausible field names is what produced dueDate/subject/assignedTo
in the first place. It is the same fault as accountCode/amount and
stageId/fields in the original seeder, and the rule is the same one: read
the consumer.

Also corrected the open-activities index added in 974, which preferred the
wrong spelling first. It read a.subject || a.text; now a.text || a.subject.
It would have worked either way, but it was written believing the wrong
names were canonical.


WHAT THIS GIVES YOU AFTER A RE-SEED
================================================================================
5% of deals overdue (red), 5% due today (green), the rest future (grey), and
an activity with a real description, a real date and an estimator's name on
it. The seeder was always generating that spread - none of it could reach
the screen.


THE RE-SEED, WHICH NOW CARRIES THREE FIXES
================================================================================
    wipe:  { action:'wipe', id:'demo', confirm:'demo' }
    seed:  { action:'seed', id:'demo', projects:30 }

posted to /api/admin/seed-demo from the browser console on a host you have an
admin session on. That one run lands:

  - the open-activities index (974), so the daily email stops claiming 142
    projects have no activity
  - readable activities with dates and owners (this package)

Still NOT in it, and both need writing if you want them:
  - PINs on the seeded Site App operatives, so the Site App can be logged
    into at all
  - projectAccess, which is [] on every operative

Say the word and those go in before you re-seed, so it is one run not two.


SMOKE TEST
================================================================================
1. CRM pipeline after re-seeding: a scatter of red and green dots, not all
   grey.
2. Open a red one: the activity has a description, a date in the past and an
   estimator's name.
3. The Activities tab - it reads the same fields and was equally empty.
