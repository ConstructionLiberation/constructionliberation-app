THE CAUSE, FROM YOUR OWN FEED
================================================================================
Two lines, in the wrong order:

    const sum = computeApplicationSummary(app, prevGross, prevReleases)   // first
    const vars = ... buildLiveVars(app, trackerVariations)                // second

A DRAFT stores `variations: []` - that array is only filled in when the
application is SENT. Your feed shows exactly that: app seq 3 (Application 5),
status draft, "variations": [].

So the summary was computed from an application with no variations, and the
variation table underneath was built afterwards and rendered them correctly.
Every figure wrong, every line present. That is why it looked like the
variations were "not pulling through" rather than like a calculation fault.

pages/applications.js has always done it the other way round:

    const workApp = { ...app, contractWorks: rows, variations: vars, materials: mats }
    const sum = computeApplicationSummary(workApp, ...)

which is why the screen was right. One rule, two implementations, opposite
order - the dominant fault class of this whole project, in a document that
goes to the customer.

Checked against your data:

    V07   5,350.37 @ 21.6424%  ->  1,157.95
    V09   1,755.00 @ 100%      ->  1,755.00
    V11     780.00 @ 100%      ->    780.00
                                  ----------
                                   3,692.95   exactly what the screen shows


WHAT ELSE THIS FIXES
================================================================================
pages/api/application-send.js uses the SAME generator, so the PDF emailed to
the customer had the same gap. That is now correct too, with no change to that
file.

Only DRAFTS were affected. A sent application has its variations frozen onto
it, so `app.variations` was populated and the summary was right.

That is worth knowing for the work already sent: those documents were correct.
The exposure was drafts - anything downloaded and sent by hand, outside the
Send to customer button.
