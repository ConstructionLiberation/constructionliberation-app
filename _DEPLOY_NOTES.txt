pkg906 - Five email functions that threw the moment they ran
============================================================

FIVE FILES, none new.
  lib/crmDailyActivityEmail.js
  lib/crmMentions.js
  lib/hsRenewalNotify.js
  lib/forEachTenant.js
  pages/api/project/[id]/cost-comments.js


THE ERROR YOUR EMAIL CAUGHT
---------------------------
    GET cron/crm-daily-activities
    Cannot access 'i' before initialization

MY FAULT, from pkg868. That package converted hardcoded URLs and addresses to
the per-customer accessors, and in five places it wrote:

    const baseUrl = baseUrl('PORTAL_BASE_URL')
    const replyTo = replyTo()

A const SHADOWS the import for the whole function INCLUDING ITS OWN RIGHT-HAND
SIDE. So the call resolves to the variable being declared, which is not
initialised yet. Minified, that reads "Cannot access 'i' before initialization".

Five of them, every one in a function that sends an email:

    lib/crmDailyActivityEmail.js   x2   the daily CRM activity emails
    lib/crmMentions.js                  mention notifications
    lib/hsRenewalNotify.js              H&S renewal reminders
    cost-comments.js                    cost comment notifications

EVERY ONE THREW THE MOMENT IT RAN. Those emails have not been going out.

Every check I have passed it: it compiles, the import graph is clean, and
`npm run build` never executes a function body. Only running it fails.


WHY IT STAYED HIDDEN FOR WEEKS - the more important half
--------------------------------------------------------
crm-daily-activities is scheduled at 06:00 AND 07:00 UTC, because only one of
those is 07:00 London whichever side of the clock change you are on. The other
exits immediately with { skipped: ... }.

The heartbeat recorded the LAST run. In BST that is always the skip.

So cron health showed:

    crm-daily-activities   ok   1ms

every single day, while the real run at 06:00 had been throwing. The failure was
not unnoticed - it was noticed and then overwritten half an hour later.

Fixed: a skipped run no longer overwrites the record of a real one. If the
stored heartbeat is a genuine run, a skip leaves it alone.

I spotted this behaviour yesterday and described it as cosmetic. It was not - it
was actively hiding a broken job. That was a bad call.


WHAT ACTUALLY FOUND IT
----------------------
pkg890, which made a failed cron iteration email you. It went in yesterday
evening; this arrived at 06:00 this morning - the first real run since.

The fault was weeks old. The reporting is one day old.
