pkg884 - IMPORTANT. Most of the app was not reading the customer's database.
============================================================================

TWO FILES, neither new.
  lib/db.js
  pages/api/admin/tenant-setup.js

WHAT SHOULD LOOK DIFFERENT AFTER DEPLOYING THIS:  NOTHING, because for Rock
both databases are the same one. That is exactly why this went unnoticed.


THE PROBLEM
-----------
lib/db.js exports 20 named helpers - getProject, saveProject, get, set,
getPortalUsers, getTokens and the rest. They are used by 164 FILES. Every one
of them called getRedis(), which returned the GLOBAL client from the
environment variables.

Only the files converted in pkg843-852 to call getClient() were resolving the
customer from the registry. Everything using a named helper - which is most of
the application - was reading whatever the environment variables pointed at,
regardless of which customer the request was for.

With one customer that is invisible: both are Rock's database. With two it is
one company seeing another's projects, and it would have been found by a
customer rather than by us.

Demonstrated, a named helper as 164 files call it:

    BEFORE    inside zztest  ->  GLOBAL          <- Rock's database
    AFTER     inside rock    ->  TENANT:rock
              inside zztest  ->  TENANT:zztest


THE FIX
-------
getRedis() now resolves the customer, instead of getClient() doing it. It is
the function every helper already calls, so all 20 follow automatically without
touching any of the 164 files.

That is the property the 49-file conversion was supposed to buy in the first
place: one function knows which database, and everything else follows without
knowing anything. I put the resolution one level too high and the conversion
could not do its job.

getClient() is now simply the client-shaped wrapper around getRedis(). Two
functions each deciding which database is two rules that can disagree. There is
one.

The identity self-check runs on this path, so every read through a helper now
also proves the database is the right customer's.


ALSO: tenant-setup.js no longer depends on the global credentials
-----------------------------------------------------------------
It used to write the identity record to "whatever the environment variables
point at". Fine with one database; a way to stamp the wrong company's database
when there are several. And it blocks removing the globals, which is the next
step.

It now names its target explicitly, in this order:

  1. credentials supplied in the request  - a new customer, not yet registered
  2. the customer is already registered   - credentials from the registry
  3. neither, and tenancy is off          - the ambient database

So provisioning customer two works like this:

    await (await fetch('/api/admin/tenant-setup', {
      method: 'POST', headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        action: 'identity', id: 'zztest', name: 'ZZ Test Construction Ltd',
        redis: { url: 'https://....upstash.io', token: '...' }
      })
    })).json()

The reply says wroteTo, naming which database was stamped, so you can see it
went where you meant.

The GET also reads the identity from the registry's credentials rather than the
environment, and reports identityReadFrom.
