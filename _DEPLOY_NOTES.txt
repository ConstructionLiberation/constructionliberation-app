WHAT IT IS
----------
/platform - the customer registry. Add a customer, set their web addresses,
switch their modules on and off, set their sender name and reply-to, point at
their database.

Deliberately plain. It is a tool for one person, used a handful of times per
customer, so it is built to be unambiguous rather than pretty.

Right now it will tell you there is no control database yet and what to do about
it. That is the correct state and it is worth seeing - it is the screen you will
come back to after the Upstash step.


WHO CAN REACH IT
----------------
Once tenancy is on: only from a platform address (PLATFORM_HOSTS) and only for
an admin. A customer's own admin must never see this - it lists every other
customer.

Until tenancy is on there IS no platform address, so an admin can reach it from
the normal portal. That is a deliberate temporary door - the registry has to be
set up from somewhere - and it closes by itself the moment TENANCY_ENABLED=1.

/platform is not in the middleware open list, so it is behind the login like
every other page.


CREDENTIALS GO IN AND NEVER COME OUT
------------------------------------
A customer's database url and token are write-only. The list shows "set" or
"missing" and nothing else, and the API strips them from every response - not
even to you. There is no screen that needs them, and a screen that shows them is
a screen that can leak them.

Editing a customer to change their modules leaves the database pointer alone.
You only type credentials when adding a customer or deliberately repointing one.


MODULES, AND WHY THEY ARE A SECOND QUESTION
-------------------------------------------
lib/roles.js already answers "may this ROLE see this area". lib/modules.js adds
the question in front: "has this CUSTOMER bought this area".

Two separate questions on purpose. A customer who has not bought Bookkeeping
should not see it whatever role someone holds; a post-contract user at a
customer who HAS bought it still should not see Business Financials. Collapse
them and a customer's purchase could grant a role access it should not have.

The module ids match the area names in lib/roles.js exactly, so one check can
ask both without a translation table. A translation table is a second copy of
the same list, and second copies diverge.

ALWAYS ON: Operations, HR, Lessons Learnt. The portal has no coherent shape
without them, so switching them off is not offered.

DEPENDENCIES ARE ENFORCED. Turning off a module another one reads does not
produce an error - it produces a page that loads with nothing in it, or a figure
computed from half its inputs. So the combination is refused at the point of
creation. Tested:

    Ops only                     ok
    Commercial + Bookkeeping     ok
    Business Financials alone    REFUSED: Business Financials needs
                                 Bookkeeping, which is switched off
    Design alone                 ok
    Everything                   ok

An address can only belong to one customer - a typo that re-points an existing
customer's address is refused with the name of the customer that already owns it.

A customer record with no module list gets EVERYTHING, not nothing. A new
customer whose modules have not been set yet should look broken to whoever is
setting them up, not to their staff.


WHAT IS NOT IN THIS PACKAGE
---------------------------
The gates themselves. Nothing yet checks hasModule() before drawing a menu item
or serving an API route - that is the next package and it touches the nav, the
pages and 169 routes.

So switching a module off here changes nothing today. The list is the record;
enforcing it comes next.

Also not here: view-as, the audit trail, and provisioning a database
automatically. Those follow.
