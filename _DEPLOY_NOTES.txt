ONE FUNCTION, NOT TWO
---------------------
An area is visible only when BOTH are true:

    the customer has bought the module      lib/modules.js
    the role is allowed the area            lib/roles.js

canSeeArea(role, area, modules) asks both. It lives in modules.js and is the
only function anyone should call. Two near-identical checks in two files is how
one gets updated and the other does not - which is the fault this project keeps
producing.

The portal learns its module list from the same call that already tells it the
role, /api/portal-auth?action=me. A separate endpoint would be a second round
trip and a second thing to forget to call.

ONE THING THAT FALLS OUT, worth knowing before you sell
-------------------------------------------------------
An ACCOUNTS user at a customer without Bookkeeping sees NOTHING. Correct by the
rules - accounts is only allowed bookkeeping and management - but they would log
in to an empty portal.

That is a provisioning warning rather than a code change: the platform admin
should say "this customer has accounts users but no Bookkeeping module". Noted
for when provisioning is built.


WHAT THIS DOES NOT DO YET - read this
-------------------------------------
IT ONLY HIDES THE TILES. Typing /bookkeeping directly still loads the page.

So this is cosmetic until the server side lands. That is the next package and it
is the bigger half: the area guard applied to the API routes, so a page reached
by URL has no data to draw and says so plainly.

23 API routes already check canAccessArea for roles - mostly the design ones -
so the pattern exists. It needs extending to modules and applying to the rest.

I would rather ship the rule and the visible half now, with that stated, than
hold both back and land 170 files at once.
