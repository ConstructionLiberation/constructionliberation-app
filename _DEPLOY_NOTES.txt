PACKAGE 931 - one customer's mail was written into another's database
================================================================================

Three files. Complete replacements. Nothing new to create.

  lib/tenantSettings.js      adds msConfigured()
  lib/crmEmailSync.js        SYNC_GROUP / BCC_MAILBOX off module scope
  lib/crmEmailVolume.js      same, and imports from the source not the re-export

CONTAINMENT FIRST - see the bottom of this file. Deploying this stops it
happening again; it does not remove what is already in zztest.


WHAT HAPPENED
=============
Found on 19 September 2026, roughly an hour after zztest was registered. The
Emails tab on the zztest portal was showing Rock Roofing's mail, and
find-string on the zztest host confirmed crm:emails:unallocated and
crm:emails:sync-state existed in zztest's own database.

Two things combined:

1. MS_TENANT_ID / MS_CLIENT_ID / MS_CLIENT_SECRET are GLOBAL environment
   variables, so the Graph token is Rock's whichever tenant is in scope.

2. lib/crmEmailSync.js line 40 was:

       export const SYNC_GROUP = msSyncGroup()

   Module scope. A module is evaluated ONCE per serverless instance, and that
   happens with NO tenant in scope - so it took the environment fallback,
   'crm-sync@rockroofing.co.uk', and stayed frozen at that value for every
   tenant the instance handled afterwards. Same for BCC_MAILBOX.

crm-email-sync loops every registered tenant. It reached zztest, used Rock's
credentials and Rock's sync group, and wrote Rock's messages into zztest's
store.

THE REDIS ISOLATION HELD THROUGHOUT. Every read and write went to the correct
database. The data crossed on a module-scope constant plus a shared credential,
which is a boundary that nothing built so far watches.

THE PART WORTH SITTING WITH: zztest's registry record has no msSyncGroup, so
fromTenant('msSyncGroup') would have THROWN and refused. The guard existed and
was correct. Evaluating at module scope meant it was never called while zztest
was in scope, so the guard never ran. The warning about this exact pattern is
written at the top of lib/tenantSettings.js, two imports away.


WHAT CHANGED
============
- SYNC_GROUP and BCC_MAILBOX are now syncGroup() and bccMailbox() - functions,
  resolved per request. Same names at every call site, one word longer.
- lib/crmEmailVolume.js no longer imports SYNC_GROUP from crmEmailSync; it calls
  msSyncGroup() from tenantSettings directly. One fewer copy of the rule.
- New msConfigured() in tenantSettings. runEmailSync() and refreshEmailVolume()
  now return { skipped: true } for a customer with no Microsoft settings rather
  than throwing. Without this the restored guard would produce an error email
  every fifteen minutes for every tenant that does not use Outlook sync.
- PRIVATE_MAILBOXES is left reading the environment, with a note. It is empty in
  your environment so it is currently harmless, but it belongs on the tenant
  record with the other Microsoft settings.

RULE TO CARRY FORWARD, and it belongs in CODE-NUANCES.md:
NEVER CALL A TENANT-AWARE FUNCTION AT MODULE SCOPE. It must be called inside the
request, every time, or it is not tenant-aware at all. I checked the rest of the
codebase: these two were the only instances.

       tenant-host:zztest.constructionliberation.com

       /api/admin/find-string?q=crm&keys=1&limit=50

   zztest database and create a fresh empty one - it holds nothing you want.
