WHY THIS HAD TO COME BEFORE THE SWITCH
--------------------------------------
When you tested the emails earlier, the two that arrived came from DIFFERENT
addresses:

    variation      Rock Roofing <notifications@send.rockroofing.co.uk>
    application    Rock Roofing Accounts <accountsreceivable@rockroofing.co.uk>

Both real, both what Watkin Jones and the rest already recognise.

The customer record held ONE sender. So the moment TENANCY_ENABLED was set,
applications would have started arriving from the notifications address -
deliverable, plausible, and quietly wrong on the document your customers pay
against.

Nobody would have noticed for weeks.


THE FIX
-------
An optional override per kind, falling back to the customer's default sender:

    Notifications and variations      notify
    Applications                      commercial
    Forms, pre-start and reports      forms
    Chase emails                      accounts

Most customers set the default and never touch these. Rock needs one, for
applications.

Proven:

    rock   notify      -> Rock Roofing <notifications@send.rockroofing.co.uk>
    rock   commercial  -> Rock Roofing Accounts <accountsreceivable@...>
    rock   forms       -> Rock Roofing <notifications@send.rockroofing.co.uk>

    wilson notify      -> Wilson Construction <notifications@...>
    wilson commercial  -> Wilson Construction <notifications@...>

A customer with no overrides gets their one sender everywhere, which is the
simple case and stays simple.

NOW REGISTER ROCK
-----------------
Two steps, in this order. Identity FIRST, so nothing is ever pointed at a
database that cannot prove who it is.

STEP 1 - stamp Rock's identity. This is a POST, so it needs the browser console
rather than the address bar. On app.rockroofing.co.uk press F12, go to Console,
and paste:

    await (await fetch('/api/admin/tenant-setup', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ action: 'identity', id: 'rock', name: 'Rock Roofing Ltd' })
    })).json()

Expect { ok: true, identity: { id: 'rock', ... } }.

STEP 2 - on /platform, press "Add a customer":

    Id                  rock
    Company name        Rock Roofing Ltd
    Web addresses       app.rockroofing.co.uk, siteapp.rockroofing.co.uk
                        BOTH - the Site App breaks without the second
    Modules             all of them
    Sender name         Rock Roofing
    Sending address     notifications@send.rockroofing.co.uk
    Applications        Rock Roofing Accounts <accountsreceivable@rockroofing.co.uk>
    Reply-to            wherever replies should go
    Timezone            Europe/London
    Database url        the value of KV_REST_API_URL
    Database token      the value of KV_REST_API_TOKEN

    Those last two are ROCK'S existing database - NOT the CONTROL_REDIS pair,
    which points at the registry itself.

STEP 3 - reload /platform. Rock should be listed, with Database "set".

NOTHING READS THAT RECORD until TENANCY_ENABLED is set, so this is safe to do
and check at your own pace. Do NOT set the switch yet - there is one more thing
I want to verify first, and I would rather look at it than find out afterwards.
