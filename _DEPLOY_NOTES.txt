FIRST: THE REPORTING WORKS
--------------------------
Your screenshot is the first real proof - route, customer, address, timestamp,
stack, sent within a minute. That endpoint was one middleware line away from
silently reporting nothing, so it was worth seeing rather than assuming.


1. ERROR EMAILS GET THEIR OWN ADDRESS
-------------------------------------
    ERROR_REPORT_EMAIL = james@constructionliberation.com

Add it in Vercel. Production and Preview. Config, not Secret - you will want to
read it back.

It is a SEPARATE variable rather than changing ALERT_EMAIL, because ALERT_EMAIL
is also where a user's "Report a problem" goes. Those want different people: a
problem report goes to whoever runs the portal for that customer; a stack trace
goes to whoever maintains the software.

Under multi-tenancy that is exactly the difference between the customer and
Construction Liberation, so it should not be one setting.

Falls back to ALERT_EMAIL if unset, so nothing stops working before you add it.


2. THE EMAIL NOW SAYS WHAT THE ROUTE SAID
-----------------------------------------
Yours said only:

    Error    Handler returned 503

Which is not enough to act on - the report route alone has two different 503s,
and I could not tell you which one you had hit.

The body the route actually sent now travels with the report, under "What the
route said". Captured by wrapping res.json, because by the time the status code
is checked the body has already gone.


3. THE 503 ITSELF
-----------------
That was the report route on J190 - the download that failed, then worked.

pkg892 made it rebuild the financial snapshot rather than refuse. It did that
with fetch() to our own deployment - which works, but is a function calling
ITSELF: a second cold start, a second serverless slot, the session cookie
forwarded by hand, and one timeout budget shared between the two. Under load
that is exactly the kind of call that fails occasionally and looks random.

It now calls the dashboard handler DIRECTLY, in the customer scope it is already
in. No second request, no cookie forwarding, no shared timeout.

And if the rebuild does fail, it now throws with the reason rather than
returning a bare 503 - so the email names the step instead of the status code.
