1. NO MORE HARDCODED ADMIN
===========================
pages/api/portal-auth.js held:

    const FIRST_ADMIN_EMAIL = 'james@rockroofing.co.uk'
    const FIRST_ADMIN_TEMP_PW = '<a literal password>'

and ensureSeed() created that account, AS AN ADMIN, in any tenant with an empty
user list, on every call to the route. A brand-new customer's portal contained
a Rock Roofing administrator whose password was a string in this repository.
Anyone who could read the source could sign in to any freshly provisioned
customer as an admin.

Confirmed on zztest on 19 September: a database with two keys in it accepted
that email and password and returned an admin session.

Both constants and the seeding are gone. A tenant with no users is now a tenant
nobody can sign in to, which is the correct state for a database that has not
been provisioned.

The first admin is created deliberately instead:

  POST /api/admin/tenant-setup
  { action: 'first-admin', id, name, email, password, redis? }

Three guards, all deliberate:

  - REFUSES if the tenant already has users. Any Rock admin can reach this
    route; without that check it would be a back door into every customer's
    portal rather than a fix for one.
  - REFUSES if the target database has no identity record, or if its identity
    disagrees with the id given. Creating an admin in an unstamped database
    means creating one in a database whose owner is unverified.
  - Password supplied by the caller, minimum 12 characters, nothing generated
    and nothing defaulted. mustResetPassword is set, so the customer changes it
    at first sign-in and whatever was typed stops being useful.

NEW-CUSTOMER.md step 10 should be updated to use this. It is now step 4a:
identity, then first-admin, then register.


2. ROCK'S INTERNAL MEETING MINUTES WERE BEING WRITTEN INTO OTHER TENANTS
========================================================================
Found while doing the above. Same fault class as pkg930, and worse in one way.

lib/lessonsSeed.js held 60 KB of Rock's real internal management meetings - two
years of them, with named staff, monthly sales figures, KPI percentages,
quality failures, and candid internal commentary of the "efficiency is dropping,
we all need to double down ways to improve gross margin" kind.

ensureSeed() in pages/api/lessons-learnt.js did:

    if (!mins || !mins.length) await set(MIN_KEY, SEED_MINUTES)

The CRM seed was rendered and discarded. This one was WRITTEN - permanently,
into the customer's own database, where it would then look like their records.
It fired the first time anyone opened Lessons Learnt on a new tenant.

Not in the client bundle, so nothing reached a browser that should not have.

The seed is now empty and ensureSeed() only writes the seen-flag.


3. NOT CHANGED, AND DELIBERATELY: lib/formDefs.js
==================================================
46 KB of form definitions with 41 "Rock Roofing" references inside the question
text, e.g. "Have you had your daily call with the Rock Roofing Contracts
Manager?". These get written into a tenant's database the same way.

Left alone because they are a DIFFERENT KIND OF THING. crmSeedDeals and
lessonsSeed are Rock's DATA and must not ship. formDefs are Rock's TEMPLATES
and genuinely are useful starting content for any roofing contractor - the
problem is only the company name inside them.

The right fix is substituting companyName() at seed time, which belongs with
the branding package rather than here. Flagged, not forgotten.
