pkg903 - One retention rule. The two pages now agree.
=====================================================

THREE FILES.

  pages/retention.js
  pages/business-financials/retentions-due.js

DEPLOY WITH pkg902 (or after it). 902 fixed the status filter; this fixes the
arithmetic underneath it. Both were needed.


WHAT WAS WRONG
--------------
Three different bases were in use:

    tracker    retention on APPLIED FOR     correct
    BF         retention on INVOICED        wrong under any reading
    tooltip    retention on FINAL ACCOUNT   wrong, and contradicted the code

Confirmed against your own rows:

    ref    tracker half   BF half    what BF was doing
    J190      7,845.91    7,993.00   319,728.17 invoiced x 5% / 2
    J197      6,914.35    6,435.00   257,390.47 invoiced x 5% / 2
    J242      6,121.68    5,657.00
    J228      2,104.11    1,429.00
    J229      1,891.83    1,892.00   applied for and invoiced nearly equal

That last row is how this survived: on the handful of jobs where applied for and
invoiced happen to match, the two pages agreed. Spot-check three of those and
everything looks fine.

BF also read STORED release1Value / release2Value, which went stale the moment
another application was sent. So it was the wrong base AND a frozen copy of it.


THE FIX
-------
lib/retentionCalc.js holds the rules, and both pages import them. Same pattern
as lib/wipCalc.js for WIP and lib/preStartDone.js for Pre-Starts - the two
places this project has already had to do it.

    calcRetentionOwed     applied for x retention %
    calcReleaseHalf       half of that, COMPUTED, never read from a stored value
    released1 / released2  manual tick beats the application
    calcOutstanding       owed less the halves released
    outstandingReleases   the unreleased halves as dated events

The list and the total come from the same function, so the cash-in list and the
outstanding figure cannot disagree by construction.

THE TOOLTIPS WERE WRONG TOO
---------------------------
Both release columns said "half of the retention on the FINAL ACCOUNT ... which
is what the contract holds and what an application certificate releases."

That is not what the code did and, per your rule, not what it should do.
Retention is deducted on what has been applied for, so the application is the
source of truth; it converges on the Final Account as the job completes. Both
tooltips now say that.

There is a note in the old code saying pkg782 set a final-account basis
deliberately and pkg785-787 rebased it onto Applied for "as a side effect rather
than as a choice". On your instruction the Applied for basis is now the choice,
and the tooltip agrees with it.
