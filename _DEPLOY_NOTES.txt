THREE THINGS WERE STOPPING IT, NOT ONE
================================================================================
The Schedule of Works filters twice, and both filters rejected everything.

1. hasContractedRates WAS FALSE ON EVERY PROJECT, EVEN THE ONE YOU UPLOADED
   RATES TO.

   dashboard.js computes that flag during a full Xero rebuild. That rebuild
   never runs on a tenant with no accounting connection, so the cached row
   still said false while the rates sat happily on the project record.

   The page is careful about this - if NO row reports the flag it shows
   everything and checks on open - but the seeded rows all carry
   `hasContractedRates: false`, so the flag counted as "known" and every
   project failed.

   Now overlaid from the live project record, using the same expression the
   rebuild uses. Third field to join that overlay after variations and
   applications in pkg1000, and the reason is identical each time: the cache
   is written by Xero, the screens are written by the app.

2. projectAccess WAS [] ON EVERY OPERATIVE.

   lib/cmSiteApp.js:

       if (pa == null || pa === 'all') return projects

   An empty ARRAY is neither. It builds an empty Set and matches nothing, so
   every seeded operative had access to NO projects. `[]` reads like "no
   restrictions" and means the exact opposite. Now 'all'.

3. AND NOBODY COULD LOG IN ANYWAY.

   No seeded operative had a `pin`, and ops-users.js compares
   String(user.pin) === String(body.pin). String(undefined) matches nothing.
   Every operative now has 1234 - the same four digits deliberately, because
   this is a demo tenant meant to be handed to someone and fifteen different
   PINs help nobody. A real tenant sets its own on invite.
