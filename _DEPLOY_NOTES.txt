pkg889 - Deep dive: eleven settings frozen at module load, and a shared flag
============================================================================

TWELVE FILES, none new.

WHAT SHOULD LOOK DIFFERENT:  NOTHING. For Rock every value resolves to what it
already was. These are faults that only appear with a second customer, which is
why they are worth finding now.


THIS IS THE DEEP DIVE YOU ASKED FOR
-----------------------------------
A deliberate hunt for the mechanical patterns that cause cross-customer leaks,
rather than a general read. Six searches:

  1. module-scope mutable state          11 found, 2 real
  2. globalThis / global                 none
  3. timers outliving a request          none server-side
  4. Redis clients outside lib/db.js     none
  5. per-customer settings resolved at   ELEVEN
     module load
  6. import-graph to server-only modules clean


FINDING 1 - ELEVEN SETTINGS FROZEN AT MODULE LOAD
-------------------------------------------------
    lib/designEmail.js          FROM, REPLY_TO, APP_URL
    lib/designRfiNotify.js      FROM, REPLY_TO, APP_URL
    lib/crmEmailVolume.js       INTERNAL_DOMAIN
    pages/api/design-oms.js     APP_URL, LOGO_URL
    pages/api/ops-users.js      FORMS_URL
    pages/api/project-process.js FROM, APP_URL

A module is evaluated ONCE, when first imported. At that moment there is no
request and therefore NO CUSTOMER IN SCOPE. So each of these froze to whatever
the environment variables said.

Every customer's design emails, RFI notices, OM notices, operative invitations
and process emails would have come from ROCK'S address with links to ROCK'S
portal - permanently, whatever their own settings said.

MY FAULT, from pkg868. That conversion replaced the call sites but did not
notice that eleven of them sit at module scope rather than inside a function. It
looked complete and achieved nothing in those eleven places.

lib/ramsNotify.js already had it right - `const FROM = () => fromEmail('forms')`
- and that was the shape to copy. All eleven are now functions, evaluated per
request with the customer resolved.

APP_URL is EXPORTED from designEmail and imported by four other files, so those
were updated too: design-calculations, design-techsubs, design-rfis,
design-rock-drawings.

WHY THIS MATTERED MORE THAN IT LOOKS: it would have survived the leak hunt. It
produces a WRONG SENDER, not wrong data on a screen. Nobody searching a database
for ZZTEST would ever have found it.


FINDING 2 - A FLAG WRITTEN BY ONE REQUEST AND READ BY ANOTHER
-------------------------------------------------------------
pages/api/crm.js had:

    let LAST_DEALS_WERE_SEED = false     // module scope

set inside loadDeals() and read later when building the response. A warm
instance serves many requests:

    request A (a customer with deals)   sets it false
    request B (a customer with none)    sets it true
    request A's response reads it       -> true

and A is told it is looking at sample data when it is not. TWO PEOPLE ON THE
PORTAL AT ONCE was enough to do it - this was a live bug before tenancy, not
only after.

The flag now travels with the array it describes, as a non-enumerable property,
so it cannot be overwritten by somebody else's request and cannot leak into
anything that serialises the deals.


FINDING 3 - THE ERROR THROTTLE IGNORED THE CUSTOMER
---------------------------------------------------
pkg887's throttle keyed on route and message only, so one company's error would
suppress another company's identical error on the same route for half an hour.
"The same error on two customers" is exactly the thing worth hearing twice. Now
keyed by customer as well.


WHAT I DID NOT FIND - worth stating
-----------------------------------
  - No globalThis or global state anywhere
  - No setInterval server-side (the three in pages/crm.js are browser-side and
    per-tab, which is correct)
  - No Redis client created outside lib/db.js and lib/tenants.js
  - No lib file touching the database at module scope
  - After these fixes, the ONLY mutable module-scope state left in the whole
    server codebase is the registry cache in lib/tenants.js - shared by design,
    identical for everyone, holds no customer data
