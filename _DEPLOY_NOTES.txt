1. THE SITE APP'S ROUTES NOW CHECK WHO IS ASKING. On the Site App address, 37
   API routes were let through and most checked nothing but the company -
   deliveries, issues, reports, tasks, projects, the dashboard's financials...
   Now a call must come from a signed-in Site App user (the token from the PIN
   sign-in), a signed-in portal user of THAT company, or the server itself.
   Left open, as on the main address: sign-in, Site App POs (their own check),
   the public RAMS approval page, downloads, scheduled jobs (cron secret), and
   Vercel Blob's signed upload callback. The check is one function, called
   whether multi-tenancy is switched on or off - placed first so an early
   return cannot skip it.
2. EVERY SITE APP SCREEN SENDS THE TOKEN - added once, in the file every Site
   App page loads, not screen by screen. An operative signed in before 1211
   (no token) is sent to the sign-in screen once, instead of screens failing.
3. SCHEDULED JOBS WERE OPEN ON THE SITE APP ADDRESS. The main address demanded
   the cron secret; the Site App address let /api/cron straight through, so
   any job (Xero sync, reports, reminder emails) could be run by anyone through
   it. Now one cron check for both addresses. (Confirmed against the previous
   middleware: "let through" before, refused now.)
4. THE SERVER'S OWN CALLS WERE BEING REFUSED. The outstanding-invoices report
   and the GP snapshot fetch /api/dashboard, and the design RFI notices fetch
   /api/planning, over HTTP with no login - so on the main address they got a
   401. They now send a private internal key (derived from the session secret,
   never sent to a browser), which both addresses accept. Those reports and
   notices should start working again. (Confirmed: the previous middleware
   refused the internal call; this one lets it through.)

AFTER DEPLOYING: operatives may be asked to sign in once more. Check that the
Site App screens load, and (next weekly run) that the outstanding-invoices
report and design RFI notices arrive.
