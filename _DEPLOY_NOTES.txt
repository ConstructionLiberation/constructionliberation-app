pkg874 - Lock the platform page to you, before the registry exists
==================================================================

TWO FILES, neither new.
  pages/api/platform/tenants.js
  pages/platform/index.js

Deploy this BEFORE creating the Upstash control database.


THE GAP
-------
pkg869 required only the admin ROLE until tenancy was switched on. That leaves a
window - between creating the control database and throwing the switch - where
any Rock admin could open /platform and read your full customer list, their
addresses and their modules.

That window could be five minutes or five weeks. "Short" was doing a lot of work
in that sentence, and this is the one screen where the blast radius is every
customer at once rather than one.


THE FIX - two independent conditions
------------------------------------
  PLATFORM_ADMINS    comma-separated emails. Yours.
  PLATFORM_HOSTS     comma-separated addresses. Your own domain.

Named people AND, once tenancy is on, the right address. Neither alone is enough.

While PLATFORM_ADMINS is unset, any admin can reach it - otherwise there would be
no way to set it up at all. SET IT AS SOON AS THE CONTROL DATABASE EXISTS.

Refusals return 404, not 403. A 403 confirms the page exists and that somebody
has access to it. A 404 says nothing.

THE PAGE NOW WARNS WHEN THE DOOR IS OPEN - an amber line saying "Any admin can
reach this page" until PLATFORM_ADMINS is set. An open door should be visible on
the screen, not only in a JSON field nobody goes looking for.


CHECKS I RAN
------------
- esbuild compile on both: 0 errors
- import-graph check: clean
- confirmed the page cannot be trusted to hide itself: it is client-side, so it
  renders its shell on any address and simply shows the API's refusal. The API
  guard is the real one; the page is only ever a view. That was true before and
  is unchanged.


WHAT TO CHECK
-------------
1. /platform as yourself - loads, with an amber warning that any admin can reach
   it. That warning is correct right now.
2. After you set PLATFORM_ADMINS, the warning goes and anyone else gets nothing.


NOW THE UPSTASH STEP
--------------------
Everything after this is unverifiable without it, so it is the right moment.

You found earlier that your database was created through Vercel rather than
Upstash directly - the kv_ prefix on your environment variables gives it away.
So create the second one the same way.

  1. Vercel project -> Storage -> create a Redis database.
     Name it something like constructionliberation-control.
     Same region as Rock's existing one.

  2. Vercel will inject its credentials under its own prefixed names, based on
     what you called the store. Copy the REST URL and REST TOKEN values into TWO
     NEW environment variables named exactly:

         CONTROL_REDIS_URL
         CONTROL_REDIS_TOKEN

     Redundant, but it keeps the code independent of whatever Vercel decides to
     call things next time. That naming has already changed more than once.

  3. Also add:

         PLATFORM_ADMINS = james@rockroofing.co.uk

  4. DO NOT add TENANCY_ENABLED. That is the switch and it comes last.

  5. Redeploy so the variables take effect, then open /platform. It should show
     an empty customer list rather than "No control database yet", and the amber
     warning should be gone.

  6. Tell me, and I will send the two calls to stamp Rock's identity and register
     it - identity first, so nothing is ever pointed at a database that cannot
     prove who it is.

While you are in that screen: check whether a second database costs anything on
your plan, and what the database limit is. You thought you were on a free tier,
and that number matters before this becomes a hundred databases.
