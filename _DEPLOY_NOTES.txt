WHAT IS IN IT
=============

1. /api/admin/find-string - the leak hunt's one dependency
--------------------------------------------------------
Read only. Writes nothing. Admin only. Wrapped in withTenant, so the same URL
on two hostnames searches two different databases - which is the whole point.

  GET /api/admin/find-string?q=<string>
      &match=<pattern>   key pattern, default *
      &limit=<n>         default 50, max 500
      &keys=1            search key NAMES too

It returns the key, the size and a short window either side of the match. It
deliberately does NOT return the matching value: a route that prints one
customer's records into a browser tab to prove they should not be there has
reproduced the leak it was built to find.

The `tenant` field in the response is the important one. A clean result is only
evidence if you know which database answered.

SMOKE TEST after deploy, on app.rockroofing.co.uk:
  /api/admin/find-string?q=Rock%20Roofing&limit=5
Expect: tenant "rock" (or whatever Rock's registry id is), some hits, and
keysScanned well above zero. If it reports 503 "No database in scope", the
route is not resolving a tenant and that is a finding in itself.


2. ALERT_EMAIL was reading the environment in four places
---------------------------------------------------------
lib/tenantSettings.js already had alertEmail(). Four files ignored it and read
process.env.ALERT_EMAIL, which has ONE value for the whole deployment. With a
second customer, their RAMS rejection / delivery note / H&S expiry with no
recipient resolved would have been posted to Rock Roofing's inbox - another
company's operational mail arriving silently.

Fixed in: lib/ramsNotify.js, pages/api/cron/deliveries-notify.js,
pages/api/cron/hs-expiry-email.js, pages/api/test-email.js.

ALSO FIXED, and this one was not on the list: alertEmail() itself returned
fromTenant('replyTo') - a copy of the function directly above it. Under one
customer those are the same address so nothing looked wrong. It now prefers the
tenant's own alertEmail and falls back to their replyTo deliberately, with the
reasoning written down. Never Rock's address.

  -> If you want a separate alert mailbox per customer, add `alertEmail` to the
     tenant record on /platform. Without it, their replyTo is used, which is
     the previous behaviour made intentional.

pages/api/test-email.js also stopped sending from the hard-coded
"Rock Roofing Sales Dashboard <onboarding@resend.dev>". It now uses
fromEmail('notify'), so the test proves THIS customer's path rather than the
deployment's.


3. sendTestMention now exists
------------------------------
pages/api/crm.js has imported it from lib/crmMentions.js since the mention work
landed. That file exported six things and never this one. SWC compiles a missing
named import to undefined, so the build passed every time and the "send test
mention" button on pages/crm-scores.js threw a 500 on every click.

It sends one real email down the identical path a real mention uses - same
resolver, same template, same sender.

SMOKE TEST: pages/crm-scores.js -> send test mention. Expect an email, and a
response carrying `testSentTo`.


4. External users are gated on the server, not just the screen
---------------------------------------------------------------
middleware.js. A design customer's session carries role 'external'. Until now
that was enforced by client-side JavaScript alone - the nav hid the rest. A
valid external session presented to /api/commercial-metrics or any of the other
~190 routes would have been accepted: signed cookie, right tenant, no role
check. Typing a URL was enough.

Allowed for external: /design*, /api/design-*, /api/portal-auth,
/api/blob-upload, and /api/planning. Everything else is 404 for APIs and a
redirect to /design for pages.

'/' is deliberately NOT allowed. pages/index.js already redirected an external
user to /design, but only after the portal home had rendered - so a customer saw
the internal home page flash up first.

>>> READ THIS ONE <<<
/api/planning is allowed because the design pages read their project list from
it. That endpoint does NOT scope its response to the customer's own projects.
So an external user can still read the operations planner. The middleware gate
closes ~190 routes and leaves this one open on purpose rather than break the
design area. Scoping /api/planning by the external user's projectAccess is the
next package, and it is the same shape as the Site App /api/site-badges problem.

SMOKE TEST: sign in as an external design user, then type /wip in the address
bar. Expect a redirect to /design, not the WIP page. Then confirm the design
area still works end to end - project list, drawings, RFIs, a file download.
