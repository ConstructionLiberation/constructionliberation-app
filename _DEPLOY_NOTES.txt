PACKAGE 984 - make the browser actually fetch the new favicon
================================================================================

One file. Complete replacement. Supersedes 983's copy.

  pages/_document.js


NOTHING WAS BROKEN
================================================================================
View source on the Site App confirmed the link is there:

    <link rel="icon" href="/api/favicon"/>

and /api/favicon on that host redirects to the CL badge. Route, middleware,
record and deployment are all correct.

The empty Network tab WAS the answer, not a failed test. Chrome keys its
favicon store on the ICON URL and keeps one for days. The URL did not
change, so Chrome never asked - which is also why incognito did not help:
the favicon database is shared, unlike the page cache.


THE FIX
================================================================================
    <link rel="icon" type="image/png" href="/api/favicon?v=2" />

The query string changes the cache key, so every browser fetches it once.
Bump v whenever the icon has to change for everyone at once.

`type` added because the route 302s to a PNG, and a browser should not have
to guess what it is about to receive from a redirect.

Middleware still matches: it tests `pathname`, which excludes the query
string, so /api/favicon?v=2 hits the same rule. Checked rather than assumed.


WHY THE PORTAL WORKED AND THE SITE APP DID NOT
================================================================================
Different origins. You had been on demo.constructionliberation.com since
before any of this, so its favicon entry was refreshed at some point;
siteapp.demo.constructionliberation.com is a separate origin whose entry was
set on your very first visit - when the tenant record was still broken - and
never revisited.
