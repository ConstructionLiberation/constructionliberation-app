FOUR HARDCODED IDENTITIES, NOT ONE
================================================================================
You spotted the names. There were four, and any one of them on its own would
have left the page looking empty:

  line  315   useState('Roman')                       the default person
  line  337   ESTIMATORS = ['Roman','Niall','James']  who counts as an estimator
  line ~423   getSalesPerson(d) === 'Edita Durikova'  the sales branch
  line 1037   ['Roman','Niall','James','Edita']       the tab strip

isEstimator was false for every demo estimator, so the estimator metric set
never rendered. And the sales branch was pinned to one name, so selecting a
different salesperson would have shown EDITA'S numbers under their name -
which is worse than showing none.


THE FIX NEEDS NO CONFIGURATION AND NO NEW DATA
================================================================================
The discriminator is already in the deals. A person is an estimator if they
appear as the estimator on a deal, and a salesperson if they appear as the
sales person. Both lists are derived, deduped and sorted; the tabs render
from them; the default is the first person who actually exists.

It cannot drift from the metrics, because the metrics filter on exactly the
fields the lists are built from.

Ran it against both shapes:

  DEMO  estimators Callum Reid, Dev Patel, Sofia Marchetti | sales Marama Tait
  ROCK  estimators James McVeigh, Niall Quinn, Roman Jarosz | sales Edita Durikova
  EMPTY no people, no tabs, no crash

ROCK WILL LOOK DIFFERENT, ON PURPOSE. The tabs will read full names rather
than "Roman" and "Edita", because that is what estimator_responsible actually
holds - the resolved portal user name. The comment at line 536 says so. A
bookmarked ?person=Roman link will fall back to the first person rather than
matching; nothing breaks, but tell anyone who has one.

Worth a look once it is live: if Rock's deals carry ex-staff in
estimator_responsible, they will each get a tab. If that list is longer than
you expect, that is the fix to make next - restrict to people with deals in
the period - and it is a two-line change.


THE SEEDER NEEDED A SALESPERSON
================================================================================
sales_person on a deal was set to the ESTIMATOR, so both derived lists would
have held the same three names and the sales tab would have duplicated an
estimator. STAFF now has a Sales role - Marama Tait - and deals point at it.


WHAT THIS DOES NOT FIX
================================================================================
pages/operations/scorecards.js still has Will, Mike and Dori as fixed
COLUMNS. Same fault, different page, and a column layout rather than a tab

And this derives the list rather than letting you edit it. Adding a person

is the smaller second step now that nothing is hardcoded.
