pkg892 - The report that downloaded as a corrupt file
=====================================================

TWO FILES, neither new. Both folders use literal square brackets.
  pages/project/[id].js
  pages/api/project/[id]/report.js


WHAT WAS HAPPENING
------------------
Excel said "cannot open the file ... the file format or file extension is not
valid".

The file was not corrupt. IT WAS A JSON ERROR MESSAGE SAVED WITH AN .xlsx
EXTENSION. Open it in Notepad and it would have said:

    {"error":"Financial data has not been built yet. Open Project Financials
    once, then download again."}

Two separate faults, one on each side.

NOT A RUSSELL HILL PROBLEM. It depends on WHEN you click, not WHICH project -
which is why it worked on the retry, and why other projects looked fine.


1. THE PAGE SAVED AN ERROR AS A SPREADSHEET
-------------------------------------------
    const res = await fetch(...)
    const blob = await res.blob()      // whatever came back
    a.download = '...xlsx'; a.click()

No check of res.ok. So any failure - 503, 500, 404 - became a file called
.xlsx, and the actual message was inside a file nobody would think to open in a
text editor.

It now reads the response first and shows the message.


2. THE REPORT REFUSED WHEN THE SNAPSHOT WAS COLD
------------------------------------------------
pkg857 made the report read the dashboard snapshot, so it cannot disagree with
what Project Financials shows. That was right.

But the snapshot EXPIRES AFTER FOUR HOURS, and the report returned 503 when it
found none - telling the user to go and open another page first.

Asking somebody to visit a different page to warm a cache is not a fix, it is a
workaround with instructions. Anyone downloading a report outside an active
working session hit it.

It now rebuilds the snapshot itself by calling /api/dashboard - the same thing
opening the page would have done, without the person needing to know that. It
calls it on the SAME ADDRESS the request arrived on, so it resolves to the same
customer, and forwards the session cookie.

If that still produces nothing, the error is now honest about it rather than
blaming the user's browsing order.


WHY THIS MATTERED MORE THAN A BROKEN DOWNLOAD
---------------------------------------------
The report was rewritten only two days ago and tested. It worked, because the
snapshot was warm at the time. The failure needed a four-hour gap to appear -
which is exactly the kind of fault that survives testing and reaches a customer.

Worth remembering when the module gates and provisioning get tested: "it worked
when I tried it" and "it works" are different claims.


CHECKS I RAN
------------
- esbuild compile on both: 0 errors
- import-graph check: clean
- confirmed the rebuild passes the incoming cookie, so the dashboard call is
  authenticated as the same user
- confirmed it uses x-forwarded-host, so under tenancy it resolves to the same
  customer rather than the deployment URL
