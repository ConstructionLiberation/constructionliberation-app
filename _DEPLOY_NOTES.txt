WHAT WAS WRONG
================================================================================
I told you this page was already routed through money(). It was not. It
imports useFormat() and takes only `companyName` off it. The money came from
line 8:

    const fmt = (n) => ... Intl.NumberFormat('en-GB', { currency: 'GBP' }) ...

Module scope, hardcoded, seven call sites. I inferred it from the file being
in the useFormat consumer list instead of reading what it destructured, which
is the read-the-consumer rule, missed.

Checking whether that was typical is the useful part: THIRTY such helpers
across TWENTY-ONE files, under six different names - fmt, fmtC, fmtP, gbp,
gbpK, money, fmtMoney. pages/project/[id].js has three of them in four lines.
One rule, thirty copies, and nobody would find the thirtieth from the first.


THE PATTERN, WHICH IS THE POINT OF THIS PACKAGE
================================================================================
A module-scope const cannot call useFormat(), because that is a hook. So:

  1. Each COMPONENT that formats money declares its own one-liner:

         const { money } = useFormat()
         const fmt = (n) => (n == null || n === '' ? '\u2014' : money(n))

     The shape stays whatever that file's helper already did - the em dash
     here, zero decimal places on sales.js, the k suffix on business
     financials. No shared abstraction to agree on, which is the trap that
     would make this take a week.

  2. Module-scope HELPERS take the formatter as an argument. This file already
     solved that problem for `brand` and wrote down why: "a missing argument
     is far easier to spot than a global that is silently wrong." Same
     pattern, same reason. resolveMergeFields() and buildBody() now take fmt,
     and all four call sites pass it.

  3. Nothing at module scope formats money any more. Verified: no GBP and no
     pound sign left in the file.

If you would rather it worked some other way, now is the moment - this is one
file, the other twenty are not written yet.


THE SERVER SIDE OF THE SAME SCREEN
================================================================================
lib/outstandingInvoicesReport.js built the weekly chase report with its own
hardcoded en-GB/GBP formatter, so the email and PDF arrived in sterling
whoever they were for. That one can read the tenant directly - it already
imports tenantSettings, so it is always inside a tenant context - and now
calls money() from lib/locale.js.

ONE THING I GOT WRONG AND CAUGHT: I first wrote that as { dp: 0 }. The old
formatter passed no fractionDigits option at all, and Intl's currency style
defaults to the CURRENCY's own digits, which is 2 - so the absence of an
option did not mean whole pounds. Ran both: old and new both give
"£1,234.50" for Rock, and "$1,234.50" for demo. Identical for Rock, which is
the property that matters.
