PACKAGE 974 - why the email says 142 and the CRM screen says none
================================================================================

One file. Complete replacement.

  lib/demoSeed.js

DEPLOYING THIS ALONE CHANGES NOTHING. It fixes what a seed WRITES; the demo
data already in the database was written by the old version. See the two
commands at the bottom.


THE CAUSE - AND YOU SPOTTED IT BY LOOKING AT A SCREEN
================================================================================
The open-activity list exists in TWO places.

  deal.activities        an array on each deal. This is what the CRM page
                         reads, which is why every deal shows an activity.

  crm:activities:open    a SEPARATE flat index across every deal, written by
                         pages/api/crm.js whenever an activity is saved
                         through the app. This is the ONLY thing the daily
                         email reads.

The seeder wrote the deals and never built the index. So on demo the index is
empty, and collectProjectsWithoutActivity() - which asks "is this deal id in
the index?" - answers no for all of them. 142 open deals not in the exempt
stage, 142 flagged, every evening, while the screen showed an activity on
every one.

Nothing was updated after 6pm. The two sources have never agreed.

This is the project-list-in-three-keys lesson wearing a new coat: one
concept, two storage locations, no shared accessor, and a screen that looks
right because it happens to read the correct one.


THE FIX
================================================================================
The seeder now builds crm:activities:open from the activities it puts on the
deals - open deals only, undone activities only. Field names copied from the
writer in pages/api/crm.js rather than invented: { id, dealId, text, due,
assignee }.

It is also added to DEMO_KEY_PREFIXES, so a wipe removes it. Without that a
re-seed would leave an index pointing at deal ids that no longer exist, which
is a worse failure than the one being fixed.

Ran the email's OWN filter against the generated index rather than eyeballing
the shape: of four test deals it flags exactly the one whose only activity is
marked done, and leaves the lost deal and the exempt-stage deal alone.


TO ACTUALLY FIX THE DEMO DATA
================================================================================
From the browser console on a host you have an admin session on:

    wipe:  { action:'wipe', id:'demo', confirm:'demo' }
    seed:  { action:'seed', id:'demo', projects:30 }

posted to /api/admin/seed-demo, as before. The data is generated, so nothing
is lost - but it IS regenerated, so any figure you have memorised from
rehearsing will change.

If you would rather not re-seed this close to Friday, the alternative is to
leave it and accept one email a day. The CRM screen is correct either way -
this only affects the email.


WORTH CHECKING ON ROCK, AND I HAVE NOT
================================================================================
The same two sources exist on Rock. There the index is maintained properly by
the app, so it should be right - but the test is free and it is the one you
just did by accident: does the number in tomorrow's email match what the CRM
actually shows? If Rock's email over-reports too, the index has drifted there
as well, and that is a different job.
