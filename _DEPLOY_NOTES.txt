PACKAGE 941 - the demo data generator
================================================================================

Two files. BOTH ARE NEW and must be created by hand in GitHub.

  lib/demoSeed.js                  the generator
  pages/api/admin/seed-demo.js     the endpoint that runs it

Nothing existing is touched. Deploying this changes nothing until you call it.


WHAT IT IS
==========
A GENERATOR, not a dataset. Every record is invented at call time from a
seeded pseudo-random sequence. There is no array of projects in the file and
no real customer data anywhere near it.

That shape is deliberate. lib/crmSeedDeals.js held 378 of Rock's real deals
and shipped them into every tenant's client bundle. lib/lessonsSeed.js held
two years of Rock's internal minutes and WROTE them into any tenant that
opened the Lessons Learnt page. Both fired automatically. This does not.

THREE GUARDS, each for something that has actually gone wrong:
  1. Never runs by itself. Only a deliberate POST naming a tenant.
  2. Refuses a tenant that already has data - dashboard:cache, ops:projects or
     crm:deals populated means it declines. Wipe first, on purpose.
  3. Refuses unless the target database's identity record agrees with the id
     given. It cannot write to a database that will not say who it is.


HOW TO USE IT
=============
Browser console on app.rockroofing.co.uk, signed in as admin.

Preview first - generates nothing, writes nothing, touches no database:

  await fetch('/api/admin/seed-demo', {
    method:'POST', headers:{'Content-Type':'application/json'},
    body: JSON.stringify({ action:'preview', projects:30, deals:48 })
  }).then(r=>r.json()).then(console.log)

Then seed:

  await fetch('/api/admin/seed-demo', {
    method:'POST', headers:{'Content-Type':'application/json'},
    body: JSON.stringify({ action:'seed', id:'demo', projects:30, deals:48 })
  }).then(r=>r.json()).then(console.log)

To start again:

  await fetch('/api/admin/seed-demo', {
    method:'POST', headers:{'Content-Type':'application/json'},
    body: JSON.stringify({ action:'wipe', id:'demo', confirm:'demo' })
  }).then(r=>r.json()).then(console.log)

Options: projects (1-60), deals (0-200), seed (any integer - the SAME seed
gives the SAME demo, so you can rehearse against a fixed dataset),
targetMargin (default 0.25).


WHAT IT GENERATES
=================
30 projects across 14 months, mixed live / defects / complete. Per project:
contract value, margin clustered on 25% with a realistic spread (a couple go
negative, because a demo where everything is profitable is not credible to
anyone who has run a contract), variations mostly instructed, monthly
applications with a gross-to-date that climbs, certified lagging slightly,
cost lines that reconcile to the margin, invoice lines that reconcile to the
applications, and retention at 3/5/10%.

Plus 48 CRM deals across seven stages, emails allocated to the first 14 deals,
nine in the unallocated review queue, nine team members and nine portal users.

Names are invented and NZ-flavoured but generic - no trade-specific language,
so the demo is not narrowed to roofing. Currency in the CRM records is NZD.

Portal users are MERGED, not replaced, so the first admin created at
provisioning survives.


THE ONE COMPROMISE, WRITTEN DOWN
=================================
It writes dashboard:cache directly.

pages/api/dashboard.js builds that cache from a LIVE Xero connection and
returns 401 before touching it when there are no tokens - so on a tenant with
no Xero the seeded cache survives and is never rebuilt. That is what makes
this possible without standing up a Xero organisation.

The cost is that projectCacheRow() in lib/demoSeed.js shadows the object
dashboard.js constructs. That is the dominant fault class in this codebase -
one rule written twice - and it is accepted deliberately. It is confined to
ONE function so there is exactly one place to update. If the commercial pages
start showing blanks after a change to dashboard.js, that function is why.


WHAT WILL BE EMPTY OR ERROR ON THE DEMO
========================================
Anything that reads Xero live rather than from the cache:
  - the sync buttons (Sync invoices, deep sync)
  - /connect and anything Xero-authenticated
  - parts of Bookkeeping and the reconciliation screens
  - Business Financials (also excluded from demo's module list)

Worth knowing which screens not to open on Friday rather than finding out in
the meeting. Forms, submissions and site photos are NOT generated yet - that
is the next package.


SMOKE TEST
==========
1. Run the preview. Check the summary reads sensibly.
2. Seed demo. Expect keysWritten around 49 and a summary.
3. On demo: Commercial, Project Financials, a project page, Retention, CRM,
   the CRM email queue. Figures should be consistent with each other -
   applications should not exceed the AFA, retention should be the stated
   percentage of the applied-for total.
4. Rock must be COMPLETELY UNTOUCHED. Check one project page and the
   dashboard. The endpoint writes only to the named tenant, but that is worth
   confirming once rather than trusting.
