pkg886 - Email me when a page breaks
====================================

TWO FILES.
  lib/errorReport.js     <-- NEW, create by hand in GitHub
  lib/withTenant.js

DEPLOY THIS BEFORE pkg885, not after. pkg885 is the package that makes routes
throw; this is the one that tells you when they do. In the other order you find
out by clicking.


WHY
-----
A failing route used to tell the user something unhelpful and tell nobody else
anything. You found out when somebody mentioned it days later - if they
mentioned it. Most people refresh, work around it, and say nothing.

That matters far more now. pkg885 makes an unwrapped route throw rather than
quietly read the wrong customer's database. A loud failure nobody hears is only
half a guardrail.

It also makes your "leave it a week and see what the team hits" plan actually
work. Without this you would be relying on eight people to notice and report a
transient error. With it, every one is an email with the route name in the
subject.


WHAT YOU GET
------------
Subject:  Portal error: /api/wip

  Route      GET /api/wip
  Customer   rock          (or "none resolved", which is the interesting one)
  Address    app.rockroofing.co.uk
  When       timestamp
  Error      the message
  Stack      first 8 lines

Sent to ALERT_EMAIL, which is already set in your project.

The user still gets a 500. This only adds the telling.


THE ONE RULE THIS OBEYS
-----------------------
The reporter must not depend on anything that might be broken.

  - It does NOT use lib/db.js. The error being reported is frequently a database
    error, and a reporter that needs the database to report a database failure
    reports nothing.
  - It does NOT use lib/tenantSettings.js. That THROWS when a customer is not
    resolved - which is exactly the error most worth hearing about.
  - It reads plain environment variables and posts straight to Resend.
  - Every failure inside it is swallowed. A reporter that can break a working
    request is worse than no reporter.


THROTTLING - so it is useful rather than unbearable
---------------------------------------------------
Held in memory per running instance, not in the database, for the reason above.
Keyed on route AND message, 30 minutes.

Tested:

  the same fault 400 times in a minute        -> 1 email
  a DIFFERENT fault on the same route         -> sent
  the same fault on a different route         -> sent
  the same fault again 31 minutes later       -> sent
  100 failures across 5 broken routes         -> 5 emails, one per route

So a click-through that finds five broken routes gives you five emails naming
them, not four hundred.

A cold start forgets the throttle and may re-send. That is the right way round:
over-reporting is noise, under-reporting is the thing this exists to prevent.


CHECKS I RAN
------------
- esbuild compile on both: 0 errors
- import-graph check: clean
- ran the throttle across five scenarios, output above
- confirmed all three paths through withTenant now go through the same guarded
  call - the platform host, the resolved customer, and the dormant single-tenant
  path - so there is one place errors are caught rather than three


WHAT THIS DOES NOT COVER YET
----------------------------
  - Crons. They record failures in their heartbeat and show in cron-health, but
    do not email. Worth adding once you have seen a week of what arrives.
  - Client-side errors. A page that breaks in the browser rather than the API
    still tells you nothing. components/PageErrorBoundary.js already catches
    them and could report - that is its own package.
  - health-check, tenant-setup and platform/tenants are not wrapped, so are not
    covered. Deliberate, and all three are yours rather than your team's.


ORDER
-----
  1. Deploy this (pkg886)
  2. Deploy pkg885 - the package that makes routes throw
  3. Click through the whole app
  4. Every broken route emails you with its name in the subject
