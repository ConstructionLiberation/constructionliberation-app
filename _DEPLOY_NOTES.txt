PACKAGE 1000 - a saved variation that never appeared
================================================================================

One file. Complete replacement. Includes 997. No re-seed.

  pages/api/dashboard.js


THIS ONE IS MINE
================================================================================
996 stopped anything deleting dashboard:cache on a tenant with no accounting
connection, because nothing could rebuild it and the commercial screens went
blank. That was right and it is why your data survived tonight.

It also had a consequence I did not think through. The Variations tracker and
the Applications screen READ from that cache but WRITE to project:<xeroId>.
Before 996, saving a variation deleted the cache, and... on demo, nothing
rebuilt it, so the screen emptied. After 996, the save succeeds and the
screen keeps showing the version from the last seed.

Saved correctly both times. Visible neither time.


THE FIX, AND WHY IT IS THE RIGHT SHAPE
================================================================================
The cache path ALREADY overlays live values from the project record - the WIP
margin override, the date overrides, the Contracts Manager - with a comment
explaining that an Ops change would otherwise not reach Project Financials
until the cache expired. Variations and applications belong in exactly that
list and were simply never added, because before multi-tenancy the
invalidation always ran and covered for it.

    ...(Array.isArray(s.variations) ? { variations: s.variations } : {}),
    ...(Array.isArray(s.applications) ? { applications: s.applications } : {}),

Only when the record actually has them, so a project whose settings carry
none does not have the cache blanked underneath it. Checked all three cases:
an edited record overlays, a missing one leaves the cache alone, and a
deliberately empty one is respected.

Better than invalidation even on Rock: an edit shows immediately instead of
triggering a full rebuild from Xero.


THE SEQUENCE THAT GOT US HERE, WORTH RECORDING
================================================================================
996  stopped the cache being destroyed        - right
1000 stopped the cache being stale instead    - the other half

I should have looked for the readers when I changed the invalidation. "What
reads this?" is the question I skipped, and it is the same question that has
been behind most of tonight.
