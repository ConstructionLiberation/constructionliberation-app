pkg924 - Variation chase emails sent customers to a Vercel login page
======================================================================

FAULT 1 - THE LINK (this is the one Jason hit)
-----------------------------------------------
The instruct link was built from the host the request arrived on:

    const origin = `${proto}://${req.headers.host}`

A cron is invoked by Vercel against the DEPLOYMENT url, not your custom
domain - which is why the link read:

    https://rock-3k4sdnhn9-rock-roofing.vercel.app/instruct/...

Vercel puts Deployment Protection in front of deployment urls, so the
customer got a Vercel sign-in page. That happens BEFORE the app runs, so
nothing in the portal could have helped him.

The first send has always worked, because a person clicks Send on
app.rockroofing.co.uk. ONLY THE CHASE WAS BROKEN - for every customer, since
this job was written.

Now uses baseUrl() from lib/tenantSettings, which resolves the customer's own
host. Its comment says exactly this: every link in an outgoing email is built
from the customer's address, never from the request. The design emails
already use it.


FAULT 2 - THE MISSING PROJECT NAME
-----------------------------------
The same email said "Reminder: Variation V03 - " and "Following up on
variation V03 for ,". The project name was blank.

It reads dashboard:cache, which has a 4-hour TTL. A cron running on a cold
cache found nothing and sent the email anyway with an empty label. Nothing
errored.

Now falls back to projects:registry - our own permanent record of every
project Xero has returned, warm cache or not - and then to the project's own
settings. Handles settings keyed by tracking option id OR job number, since
either can be the key.

AFTER DEPLOYING - CHECK
-----------------------
/api/cron/variation-reminders?dry=1 reports what it WOULD send without
sending anything. It will not show the link, so to prove the fix, find a
variation due a chase and use ?force=1 on one you are willing to email -
or simply check the next real chase that goes out.

The subject line should carry the job number and project name.


STILL BROKEN, SAME SHAPE, NOT IN THIS PACKAGE
----------------------------------------------
Every emailed link built from req.headers.host has this fault whenever a cron
generates it. Human-initiated sends are fine because they come from the right
domain. The list: application-send, pre-start-send, pre-start-notify-send,
issue-notify, issue-send-customer, rams-approvals, portal-auth (password
resets), ops-scorecards, bookkeeping-inquery.

Worth a package of its own. Not bundled here because this one is a live
customer problem and should go out on its own.

A related one worth knowing: PDFs built by crons fetch the logo from the same
deployment url, and Deployment Protection blocks that too - so cron-generated
PDFs may be missing the logo. Cosmetic, same cause.
