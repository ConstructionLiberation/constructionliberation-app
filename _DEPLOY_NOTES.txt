pkg879 - Stop an endpoint printing Rock's database token
========================================================

ONE FILE.  pages/api/admin/tenant-setup.js  - not new.

DEPLOY BEFORE RUNNING THE PRE-FLIGHT CHECK. I was about to ask you to open that
endpoint and paste the output to me.


WHAT IT WAS DOING
-----------------
The GET returned resolvedForThisHost as the RAW customer record - which carries

    redis: { url, token }

So it would have printed Rock's database url and access token into a browser
tab, and into anything that output was pasted into. Including this chat.

Admin-only, so not exposed to the world. But a credential in a response is a
credential in a screenshot, a support ticket, a scroll-back.

pages/api/platform/tenants.js has ALWAYS stripped credentials - it has a safe()
helper and uses it on every response. tenant-setup.js was written earlier and
never got one. Same rule, two places, one of them wrong.

That is the fault class this project keeps producing. This time it was
credentials rather than a number.


THE FIX
-------
A safeTenant() helper, applied before responding. The record still tells you
everything useful - id, name, hosts, modules, timezone - plus

    databaseConfigured: true | false

which is the only thing anyone needs to know about the credentials.


CHECKS I RAN
------------
- esbuild compile: 0 errors
- grepped every endpoint that reads a tenant record and checked each one either
  strips before responding or uses the record internally only. Three internal
  uses in platform/tenants.js, both responses already stripped, this one fixed.


AFTER DEPLOYING - THE PRE-FLIGHT CHECK
--------------------------------------
This is the last thing before the switch, and it is the one that matters.

Open, as admin, on app.rockroofing.co.uk:

    /api/admin/tenant-setup

You are looking for FOUR things:

    controlDatabaseConfigured : true
    tenancyEnabled            : false
    identityOfCurrentDatabase : { id: "rock", name: "Rock Roofing Ltd", ... }
    resolvedForThisHost       : { id: "rock", ..., databaseConfigured: true }

The last two are the two halves of the self-check, and this is the first time
they can be compared.

    identityOfCurrentDatabase   what the DATABASE says it is
    resolvedForThisHost         what the REGISTRY says this address is

BOTH MUST SAY "rock". If they do, the mapping is right and the switch is safe.
If resolvedForThisHost comes back null, the address in the registry does not
match the address you are browsing - fixable in the platform page, and far
better found now than after the switch, when every request would 404.

Safe to paste the whole thing to me now.
