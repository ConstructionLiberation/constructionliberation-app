PACKAGE 956 - the customer's timezone reaches the browser
================================================================================

Three files. Complete replacements. NOTHING ON SCREEN CHANGES.

  lib/locale.js
  pages/api/tenant-brand.js
  components/TenantProvider.js

This is plumbing. It is worth deploying on its own because it changes no
behaviour for anybody, and nothing else on the date work can be built until
the value is on the feed.


READ THIS FIRST - MY ESTIMATE WAS WRONG
================================================================================
I told you the timezone fix was "a resolver plus the hardcoded sites, not a
rewrite". That was wrong, and wrong in the direction that matters.

EVERY consumer of lib/businessDate.js is a CLIENT page. Not one API route
calls it. So the timezone cannot come from currentTenant() - it has to travel
over the brand feed, which is what this package does.

And on the client the value is not simply read, it is FROZEN:

  pages/project-cashflow.js          4 call sites, one inside useState
  pages/operations/.../planning.js  12 call sites, two inside useState, 1,800 lines
  pages/business-financials/cashflow.js  7 sites behind a MODULE-SCOPE helper
                                         `const todayISO = () => businessToday()`
  pages/operations/forms-missing.js  2 sites
  pages/forms/cm/missing-forms.js    1 site

A value read into useState, or into a useMemo whose deps do not include the
feed, keeps the first answer it ever got - which is London - for the life of
the page. That is the same fault as module-scope evaluation, one layer up.

So the remaining work is a page-by-page job on two of the largest files in the
repo, not a sweep. See the note at the bottom.


WHAT THIS PACKAGE DOES
================================================================================
lib/locale.js gains businessTimezone(). An explicit `timezone` on the tenant
record wins, exactly as `currency` does. An INVALID one does not - it falls
through to the locale default rather than throwing inside Intl on every date
on the page. Defaults: UK Europe/London, US America/New_York, AU
Australia/Sydney, NZ Pacific/Auckland.

/api/tenant-brand now carries `timezone`. It is not sensitive - it is on the
customer's contact page - and it is the only route the value has to a browser.

TenantProvider exposes businessToday(), businessNow() and businessDay() bound
to the customer's timezone, so a page calls them with no argument and gets the
right answer. It IMPORTS lib/businessDate rather than reimplementing it:
that file imports nothing and is pure Intl, so it is the same code both sides.
Checked that it drags no async_hooks into the browser bundle.


TWO RECORD EDITS, BOTH IN THE CONTROL DATABASE
================================================================================
On tenant:demo:

    "timezone": "Pacific/Auckland"

It currently says Europe/London on a tenant whose locale is NZ. Note the
explicit value WINS over the locale default, so this has to be corrected by
hand - the code will not quietly override it, on purpose.

Also on tenant:demo, add to `modules`:

    "business-financials"

Rock has it and demo does not. That switches the area on; the data is a
separate job (see below).

Nothing to change on tenant:rock. Rock is Europe/London either way, which is
the safety property of this whole piece of work: for Rock, every one of these
functions returns exactly what it returned before.


WHY IT MATTERS, WITH THE ACTUAL NUMBERS
================================================================================
New Zealand is UTC+12 until 27 September, then UTC+13. So the London date and
the Auckland date differ whenever it is between 12:00 and midnight in London.

A demo at 9am Friday in Auckland is 9pm Thursday in London. Every "today",
every week anchor and every overdue flag on the screen would say Thursday.

  crmDailyActivityEmail, outstandingInvoicesReport, designRfiNotify,
  hsRenewalNotify, and four design approval `atText` stamps.

  internal hour gate (hs-renewals, crm-daily-activities) show the right
  pattern, but converting the rest is its own piece of work.
- The ICS invite in concern-invite.js is hardcoded TZID:Europe/London, and
  ProjectConcerns.js tells the user so in as many words.
