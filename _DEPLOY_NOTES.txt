pkg891 - Variations default to not instructed, and the retention import stops
              dropping rows silently
==============================================================================

THREE FILES, none new.
  pages/variations.js
  pages/retention.js
  pages/api/retention.js


1. A MANUALLY ADDED VARIATION IS NOT INSTRUCTED
-----------------------------------------------
The Add dialog defaulted to instructed = yes. So anything typed straight into
the tracker counted as AUTHORISED BY THE CUSTOMER the moment it was saved - into
the AFA, the applications and the margin, without anyone having agreed it.

Worse, it was not easily undone: pages/api/project/[id]/settings.js refuses to
delete or change an instructed variation, which is the guard you met on Sunday.
So a mis-added row was stuck.

Not instructed is the honest starting point - it was raised, nobody has agreed
it yet. Tick it when they have.

The default existed in THREE places - the initial state, the reset after saving,
and the reset when the dialog opens. There is now one constant used by all
three, because three copies of a default is three chances to change two of them.


2. THE RETENTION IMPORT SILENTLY DROPPED ROWS
---------------------------------------------
You asked me to check the import and manual entry without testing them. This is
what I found.

The import filters out every row with no ourRef, and says nothing:

    const incoming = req.body.entries.filter(e => e && String(e.ourRef||'').trim())

Import a hundred rows, twelve missing a reference, and the message said
"88 added" with no mention of the twelve. Nobody counts rows afterwards, and a
retention row that never arrived looks exactly like one that was never there.

Rows are still skipped - ourRef is what rows are matched on, and a row without
one could never be updated later. But the reply now returns a count AND the
first twenty by name, and the page says:

    Imported 100 rows - 85 added, 3 updated, 12 SKIPPED with no reference:
    Gas Lane, Waungron, ...


3. WHAT I CHECKED AND FOUND SOUND
---------------------------------
  - The import NEVER DELETES. It only adds and merges, so a bad import cannot
    empty the tracker.
  - Existing rows are matched on ourRef, trimmed and lower-cased, and merged
    with `{ ...existing, ...incoming, id: existing.id }` - so the id is
    preserved and a re-import updates rather than duplicating.
  - The manual entry path generates its own id and appends. Update merges by id.
  - The read-modify-write window on the entries array is TIGHT - the read and
    the write have no await between them. This is the same shape as the fault
    that lost the Gas Lane application, but there it had a PDF build and an
    email in the middle, several seconds wide. Here it is microseconds. Not
    worth changing.
  - Only comments are written back to the project record; everything else is
    read-only from the project. So the tracker cannot corrupt a project.

ONE THING I COULD NOT CHECK from here: whether a BLANK CELL in the spreadsheet
overwrites an existing value with an empty string. That depends on how the page
builds each row before sending. If you ever import a partial sheet - say just
references and dates - and find other columns blanked, that is the cause and it
is a one-line fix.
