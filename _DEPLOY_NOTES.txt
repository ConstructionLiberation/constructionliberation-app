PACKAGE 1015 - applications going out without their variations
================================================================================

*** DEPLOY THIS BEFORE SENDING ANY MORE APPLICATIONS ***

Three files. One is NEW. Rock-live, no re-seed.

  lib/projectRecord.js         <- NEW
  pages/api/application-pdf.js
  pages/api/application-send.js   <- includes 975 and 1004


WHAT YOU FOUND
================================================================================
Two requests, same project, different ids:

    applications?projectId=0f7f23f3-...   1.3 kB   empty skeleton
    applications?projectId=daa57815-...   8.5 kB   the real record

A project answers to more than one id. The dashboard cache row carries both
`xeroId` and `trackingOptionId` and they are NOT always the same value.
getProject() answers for exactly the key it is given and returns an EMPTY
OBJECT - not an error - for the other one.

The screen had resolved to the id with the record behind it. The Download PDF
link still carried the one that did not. So every figure that comes off the
APPLICATION was correct, and everything that comes off the PROJECT - the
variations, the customer name - was silently absent.

On J240 that is 3,692.95 of variations missing from a document that goes to
the customer, with nothing on the page or the PDF to suggest anything was
wrong. You said others are affected; any project whose two ids differ behaves
the same way.


THE FIX
================================================================================
lib/projectRecord.js resolves a project record from ANY id it answers to:
tries the key given, then finds the project in the dashboard cache by either
id, then tries the others including job number, then falls back to searching
the settings map by job number.

Checked against the exact shape you are seeing:

    given the id WITH a record     -> that record, 3 variations
    given the id WITHOUT one       -> the same record, 3 variations
    given an id nobody knows       -> empty, as before

pages/api/project/[id].js has resolved across both ids when reading the CACHE
for a while. Nothing did it for the SETTINGS record. One rule, two places,
only one of them implemented - the same shape as most of this fortnight.


THE WRITE MATTERED MORE THAN THE READ
================================================================================
application-send.js re-reads and saves the project when an application is
marked sent. That used the caller's id for both. Left alone, this fix would
have made it read the GOOD record and write to the EMPTY one - creating a
second record and storing the sent application where nothing reads it.

It now reads and writes the SAME resolved key. If you deploy only part of this
package, deploy that file.


WHAT TO CHECK ON WORK ALREADY SENT
================================================================================
Any application SENT on an affected project will have frozen its variations
from the empty record, so the stored record of what was claimed is also short.
Worth opening a few sent applications on projects other than J240 and
comparing the variations on the certificate against the tracker.

I have not written anything to correct historical records - that needs your
decision, and it should be deliberate rather than a side effect of a fix.
