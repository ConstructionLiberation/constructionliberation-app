pkg927 - Catch a bad link in an outgoing email before a customer does
======================================================================

ONE NEW FILE - CREATE THIS MANUALLY:

  lib/linkGuard.js

REPLACE (2 files, both existing):

  pages/api/application-send.js
  pages/api/variation-send.js


WHAT IT IS
----------
An invariant check: every link in an email to somebody outside the business
must be on a host we own.

Tonight's fault produced NO ERROR. The cron succeeded, Resend accepted the
email, every figure in it was correct - and the link led to a Vercel sign-in
page. Error reporting and cron health cannot catch that, because nothing
went wrong. An invariant can.

Tested against the actual email Jason received: it flags
rock-3k4sdnhn9-rock-roofing.vercel.app. A correct email, a mailto, a blob
attachment link and a relative link all pass clean.


IT WARNS, IT DOES NOT BLOCK
----------------------------
The email still sends. You get an error email naming the route and the
offending host.

Deliberate: if the host list were ever incomplete, a blocking guard means a
customer gets NO application at all, which is worse than a bad link. Let it
run a week. If nothing false fires, change BLOCK to true at the top of
lib/linkGuard.js and it starts refusing instead. That one line is the whole
switch.

The check can never break a send - it is wrapped so that a fault in the
guard itself is swallowed.


COVERAGE - PARTIAL, AND HERE IS EXACTLY WHAT IS NOT COVERED
------------------------------------------------------------
32 files call Resend directly. There is no shared send helper, and the
payload shape differs in each, so wiring all 32 is a large change with 32
chances to break a send. Not something to do at the end of a long session.

COVERED:   application-send, variation-send
           (variation-reminders needs no guard - pkg926 fixed it at source)

NOT COVERED YET: pre-start-send, pre-start-notify-send, rams-approvals,
           issue-notify, issue-send-customer, bookkeeping-inquery,
           portal-auth (password resets), ops-scorecards, concern-invite,
           chase-email-send, deliveries-notify, forms-weekly-notify,
           hs-expiry-email, outstanding-invoices, ops-users, report-problem,
           wip-lock, variation-instruct

The real answer is one shared sendEmail() helper that every route uses, with
this check inside it. That is the job worth doing, and it is its own package.


AFTER DEPLOYING - CHECK
-----------------------
1. Send a variation and an application as normal. Both should behave exactly
   as before - the guard only reports.
2. You should NOT receive an error email. If you do, it has found a real one
   and the email names the route and the host.
