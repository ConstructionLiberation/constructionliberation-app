PACKAGE 981 - the Site App installs under the customer's name
================================================================================

Three files. ONE IS NEW.

  pages/api/site-webmanifest.js   <- NEW
  pages/_document.js
  middleware.js                   <- repo root

No overlap with 979 or 980; all three can go together.


WHAT WAS WRONG
================================================================================
public/site.webmanifest is ONE static file served to every tenant, and it
says:

    "name": "Rock Roofing", "short_name": "Rock Roofing"

That is what appears under the icon when an operative adds the Site App to
their phone. Every customer's phone would install it as Rock Roofing, and
demo's already would.

No component can fix it. The phone's OS fetches the manifest directly, so
this is the one piece of branding React never sees.


THE FIX
================================================================================
A route that builds the manifest per tenant, and _document.js points at it.
Unauthenticated for the same reason /api/tenant-brand is - the browser asks
for the manifest on first paint, including on the login page, possibly
without cookies. It therefore returns only a name and an icon, written out
field by field so nothing added to the tenant record later can leak.


MIDDLEWARE - AND THIS IS THE PART THAT WOULD HAVE BROKEN IT SILENTLY
================================================================================
Both passthrough lists match static files BY EXTENSION:

    /\.(webmanifest|ico|png|jpg|...)$/i.test(pathname)

An API route has no extension. So without the middleware change, on the Site
App host the manifest request is rewritten to the /forms PAGE, and on the
portal it is redirected to /login - which is EXACTLY the bug the comment at
that line already describes happening to the static file once before:
"the browser asked for JSON and got an HTML page".

Added to both lists explicitly.


ICONS DELIBERATELY DO NOT COME FROM logoUrl
================================================================================
I checked what Rock actually installs: favicon-512.png, a square green ROCK
mark. Its logoUrl is a 565px JPEG - a different image for a different job. A
home-screen icon is square, masked to a circle or squircle by the phone, and
wants 192 and 512.

So the icon comes from an OPTIONAL `iconUrl` on the tenant record and falls
back to the existing static files. A tenant that sets nothing keeps exactly
what it has today, which for Rock means nothing changes at all.

To give demo the CL badge, add to tenant:demo:

    "iconUrl": "/cl-logo.png"

Optionally also "shortName" if you want something shorter than the company
name under the icon - there is room for about twelve characters. "Demo" fits
already, so demo needs nothing.


RENDERED FOR ALL THREE CASES RATHER THAN EYEBALLED
================================================================================
  Rock, no iconUrl   name "Rock Roofing", icons favicon-192 and favicon-512
  demo with iconUrl  name "Demo", icon /cl-logo.png
  no tenant          name "Portal", static icons


public/site.webmanifest IS LEFT IN PLACE
================================================================================
Nothing references it now, but a phone that has already installed the app
may still ask for the old URL. Deleting it buys nothing and could 404 an
existing install.


SMOKE TEST
================================================================================
1. Open /api/site-webmanifest on Rock - JSON, name "Rock Roofing", the two
   favicon entries.
2. Same on demo.constructionliberation.com - "Demo".
3. Same on siteapp.demo.constructionliberation.com. THIS IS THE ONE THE
   MIDDLEWARE CHANGE IS FOR - if it returns HTML, the middleware file did not
   go up.
4. On a phone, add the demo Site App to the home screen. It should say Demo.
5. Rock: no manifest error in the console on any page, and an existing
   installed app unchanged.
