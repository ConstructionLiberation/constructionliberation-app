PACKAGE 1020 - the three Site App report faults
================================================================================

Two files. Complete replacements. Both supersede their copies in 1019.
No re-seed, no file deletions.

  pages/api/project-report-template.js
  pages/forms/cm/reports.js


1. TEMPLATE SECTIONS MISSING ON A NEW SITE APP REPORT
================================================================================
The template route required a portal role:

    const READ = ['pre-contract','post-contract','accounts','management','admin']

A Site App operative has no portal session, so requireRole answered 401 - and
the page did:

    .catch(() => {})

so the sections simply never appeared. A report written on a phone was
missing every box the customer had added, and nothing anywhere said why.

That is my own swallowed response, in a file whose comments make a point
about checking them. Twice over: the guard was wrong AND the failure was
hidden.

Reading the template now needs no session at all - the same as /api/srats,
and for the same reason. What it returns is a list of HEADINGS: no project
data, no figures, nothing about a customer. Writing it still needs management
or admin.

The page now checks the response and says so if it ever fails again.


2. EDITING A COMPLETED PORTAL REPORT OPENED BLANK
================================================================================
GET /api/project-reports without an id returns a LIGHT INDEX - id, reportId,
project, status, date - deliberately dropping worksCompleted, siteComms, the
extra sections, the snapshots and the photos. The comment in that route says
"drop heavy fields".

1019 handed a row of that index straight to the form. Every field the index
drops was therefore empty, which looks exactly like a blank report.

The portal has always fetched the full record by id before opening it. The
Site App now does the same, and reports a failure instead of opening an empty
form.

Worth noting what would have happened next: saving that blank form would have
written the empty fields back over a completed report. The fault was one tap
away from destroying a submitted document.


3. COMPLETED REPORTS CAN NOW BE VIEWED
================================================================================
Each card has View, Edit and Delete. View is read-only and shows the whole
thing - site communications, works completed, the customer's own sections,
variations, issues, every photo and who approved it - with Edit one tap away.

Reading the last report before writing the next is the common thing to want
on site, and it should not require opening an editor over a document somebody
has already signed off.


SMOKE TEST
================================================================================
1. Add a section to the template in the portal.
2. Site App, new project report: the section appears. It did not before.
3. Site App: View a report completed in the portal - everything shows,
   including its own sections and photos.
4. Site App: Edit that same report - the fields are POPULATED, not blank.
5. Change one word, submit, and check the portal shows the change and has not
   lost anything else.
6. Turn the template route off at the server for a moment if you like - the
   page should say it could not load the template rather than quietly drop
   the sections.
